# dbmock

`dbmock` 是 `insight` 项目的电商数仓数据构建工具，用于在 Apache Doris 中生成一套可查询、可关联、可验证的中国中小型综合电商平台数据

项目以真实公开商品目录为基础，按照统一业务时间线生成用户、流量、营销、交易、支付、履约、退款和库存数据，主要用于数据分析 Agent 开发、语义检索、指标验证和数仓查询测试

> 商品、品牌、类目、店铺和 SKU 规格来自真实公开页面；用户及业务事实由规则模型生成。项目追求业务关系和统计分布的真实性，不将生成数据冒充真实平台交易记录

## 核心能力

- 构建截止任务执行日期、向前覆盖两年的完整业务数据
- 使用国内公开商品页面准备 5,000 个 SPU 及其真实 SKU
- 按月编排、逐日演化业务状态，支持跨日和跨月业务链路
- 生成从会话、浏览、搜索、收藏、购物车到订单的用户行为路径
- 闭合订单、优惠、支付、配送、退款、评价和库存之间的关联关系
- 使用 SCD2 保存用户、商家、店铺、类目、商品和仓库等维度变化
- 通过 PyArrow Parquet 和 Doris Stream Load 并发写入大规模数据
- 对时间顺序、金额分摊、状态流转、外键和数据分布执行自动质量校验

## 数据真实性边界

| 类型 | 主要内容 | 处理原则 |
| --- | --- | --- |
| 真实采集数据 | 商品标题、品牌、店铺、来源类目、公开参数、SPU/SKU 关系、SKU 规格、价格、图片和来源链接 | 保留来源标识、采集时间和字段血缘，不补造源站未公开字段 |
| 平台标准化数据 | 内部商品、品牌、类目、商家和店铺 ID，平台三级类目及名称归一结果 | 使用稳定映射，保留原始值与标准值的对应关系 |
| 业务生成数据 | 用户、营销、行为、订单、支付、履约、退款、评价、成本和库存 | 由状态和业务规则驱动，满足时间、金额、数量和状态约束 |

外部页面无法验证的评分、地址、重量等字段不会伪装成真实采集值。平台内部成本、库存和脱敏地址等数据会明确按照业务模型生成

## 数仓模型

项目在 Doris 中创建 45 张业务表，覆盖以下主题域：

- 公共维度：日期、渠道、页面、行政区划、支付方式和物流公司
- 用户域：用户拉链维度、用户标签及标签关系
- 商品域：SPU、SKU、品牌、类目、商家、店铺和价格变更
- 营销域：促销规则、优惠券模板、适用范围和用户券生命周期
- 流量域：会话、页面访问、搜索和搜索点击
- 互动域：收藏、取消收藏及购物车增删改清
- 交易域：订单明细、订单状态、活动优惠和优惠券分摊
- 支付域：支付明细、订单分摊及支付状态
- 履约域：配送单、配送商品和配送状态
- 售后域：退款、退款状态、退款支付和评价
- 库存域：库存变更流水和 SKU 日末库存快照

表名遵循以下约定：

- `dim_*_zip`：SCD2 拉链维度
- `dim_*`：普通维度或版本维度
- `bridge_*`：多对多关系桥接表
- `dwd_*_di`：明细事件事实表
- `dwd_*_df`：全量日快照表

完整 DDL 位于 `scripts/sql/ecommerce.sql`

## 生成机制

```text
真实商品目录
  ↓
公共维度、用户维度和商品维度
  ↓
营销规则与优惠券
  ↓
按月编排，逐日生成
  ↓
会话 → 浏览／搜索 → 收藏／购物车 → 订单
  ↓
库存预占 → 支付 → 配送 → 退款／评价
  ↓
采购补货、退货入库和库存日末快照
  ↓
跨表质量校验
```

生成过程遵循以下时间和状态语义：

- 截止时间取任务实际启动时的 `Asia/Shanghai` 日期和时刻
- 开始日期为截止日期向前两个自然年，首尾日期均包含
- 业务事实只有到达实际发生时间后才会写入 Doris
- 截止时刻尚未完成的订单、配送和退款会保留为合理的中间状态
- 跨月订单、库存、用户和营销状态在同一次进程中持续继承
- 事务事实、日快照和维度分别使用符合其处理方式的入仓延迟
- 历史数据的入仓时间不会统一等于本次任务执行时间
- 法定节假日和调休工作日由 `chinese-calendar` 提供，超出支持年份时直接报错

每个月的数据先在内存中生成，再按表切分为最多 250,000 行的 Parquet 批次，通过 4 个工作线程执行 Doris Stream Load。库存日快照由 Doris 根据库存流水集合计算，避免在 Python 中逐 SKU、逐日写入

## 环境要求

- Python 3.12 或更高版本
- `uv`
- Apache Doris 4.0 或更高版本
- 当前主机能够访问 Doris FE 的 `9030`、`8030` 端口和 BE 的 `8040` 端口

安装依赖并创建本地配置：

```bash
cd dbmock
cp .env.example .env
uv sync
```

`.env` 只保存 Doris 连接信息，所有字段都必须显式提供：

```dotenv
DB_HOST="127.0.0.1"
DB_PORT=9030
DB_USER="root"
DB_PASSWORD=""
DB_NAME="ecommerce"
```

Doris FE HTTP 端口目前在 `src/settings.py` 中配置为 `8030`

## 快速开始

### 1. 准备商品目录

首次使用或需要重新采集时执行：

```bash
uv run python -m collection
```

已有本地目录时可以只做完整性和质量校验：

```bash
uv run python -m collection --validate-only
```

清空采集断点并重新采集：

```bash
uv run python -m collection --force-download
```

采集过程使用 `data/source/` 保存断点、来源缓存和原始页面，目录准备成功后会自动删除这些中间数据。最终商品维度、来源业务血缘和目录清单保存在 `data/` 根目录，并通过 Git LFS 跟踪

### 2. 初始化 Doris

```bash
make init_db
```

该命令会删除并重建 `.env` 中 `DB_NAME` 指定的数据库，然后执行全部业务表 DDL。请勿将其指向需要保留的数据库

### 3. 验证完整链路

```bash
make smoke
```

smoke 模式生成最近七天的小规模数据，并执行与全量任务相同的业务链路和质量校验

### 4. 生成两年全量数据

```bash
make init_db
make generate
```

smoke 数据不能与全量数据共存，因此正式生成前需要重新初始化数据库。生成任务要求全部业务表为空。默认规模在本地 Docker Doris 环境中通常需要十几分钟，实际耗时取决于 CPU、内存、磁盘和 Doris 负载

### 5. 校验现有数据

```bash
make validate
```

质量报告写入 `data/quality_report.json`，该文件是本地验收产物，不写入 Doris

如需只加载公共维度和商品维度，可以执行：

```bash
make init_db
uv run main.py --dimensions-only
```

## 质量保障

全量生成完成后会自动验证：

- 必填表、未知维度成员、SCD2 区间和当前版本
- 商品、品牌、类目、店铺、用户及业务事实的外键完整性
- 会话、页面、搜索、点击、收藏、购物车和订单的时间边界
- 订单、优惠券、活动、支付、配送和退款的金额及数量分摊
- 订单、支付、配送和退款状态的先后顺序与终态闭合
- 库存预占、释放、出库、退货和补货的数量连续性
- 缺货取消与真实库存分配失败之间的因果关系
- 库存流水与日末库存快照的一致性
- 业务时间、入仓时间、业务月份和装载批次的一致性
- 转化率、支付成功率、退款率、优惠率和库存暴露等分布指标
- 购物车放弃和修改、取消收藏、用户沉默及流失等非理想路径

任何硬性关系错误都会使生成任务失败。分布指标使用区间阈值识别过于机械或偏离平台画像的数据

## 运行限制

- 项目不保存生成检查点，也不支持中断恢复
- 任务失败后应执行 `make init_db`，再重新运行 smoke 或全量生成
- 跨月状态只在当前生成进程中继承，不写入 Doris 技术表或本地状态文件
- `data/` 通过 Git LFS 分发，新环境需要安装 Git LFS，并在拉取仓库后执行 `git lfs pull`
- 商品采集应遵守来源网站的公开访问规则、使用条款和请求频率限制
- 生成数据用于开发和测试，不应作为真实经营数据或生产决策依据
