# 身份

## 1. 领域职责

身份模块把应用用户映射到 Doris 查询账号，并把实际 SELECT 授权转换为元数据可见策略。会话和文件使用应用用户 ID 归属，业务 SQL 使用 Doris 查询账号执行。

前端从预定义用户列表中选择身份，后续请求携带 X-User-ID。后端验证标识有效且用户存在。该标识用于身份选择。

## 2. 数据模型

| 模型                   | 关键字段                                                               | 作用                       |
| ---------------------- | ---------------------------------------------------------------------- | -------------------------- |
| User                   | id、username、doris_role_name                                          | 应用用户及其查询角色       |
| DorisQueryIdentity     | role_name、query_user、encrypted_password、workload_group、description | 角色对应的查询账号和凭据   |
| ResolvedQueryPrincipal | role_name、query_user、password                                        | 一次查询可用的已解密身份   |
| AssetIdentity          | 数据源、库、表、字段                                                   | 一个数据资产或授权范围     |
| AssetAccessPolicy      | grants                                                                 | 一组 SELECT 授权的判定入口 |

User 使用预定义 ID，用户名唯一。角色名引用查询身份记录；查询身份以角色名为主键，查询账号唯一。这个结构允许多个应用用户引用同一角色，而会话依然按各自用户 ID 隔离。

查询凭据是运行资源配置，授权范围来自 Doris。描述字段只负责说明角色用途，不参与权限计算。

## 4. 初始化流程

bootstrap_users 使用 RolePreset 和预定义用户集合创建身份。执行入口为 `uv run -m scripts.bootstrap_users`。

处理每个角色时，脚本先在身份数据库中保存或读取查询凭据；已有记录沿用原密码。随后创建 Doris 角色，授予业务表 SELECT_PRIV 及 normal 工作组 USAGE_PRIV，创建查询账号、将其密码设为已保存值并绑定角色。全部角色准备完成后，才在一个事务中写入预定义用户关联。

先保存凭据使 Doris 初始化失败后重跑能沿用同一密码。新用户在角色全部就绪后才发布，避免前端选择到初始化尚未完成的新身份；已有用户仍可能受中途授权变更影响。

admin 的表范围为整个配置业务库；受限角色逐表授权。所有角色定位为业务查询身份，不因名字包含 admin 就获得业务写入能力。

初始化跨越 Doris 和 PostgreSQL，不是统一事务。脚本支持重复运行，但授权是追加语义：从预定义清单删除一张表不会自动执行 REVOKE。收缩权限需要显式回收现存授权后再验证实际结果。

## 5. 查询身份解析

IdentityService.get_query_principal 先查 User，再按 doris_role_name 查 DorisQueryIdentity，然后通过 DorisCredentialCipher 解密密码，返回 ResolvedQueryPrincipal。

用户不存在会要求重新选择身份；用户已经存在但角色查询身份缺失，会报告查询身份未配置。两种问题发生在 SQL 执行前，应分别排查用户初始化和角色关联。

DorisQueryClientRegistry 用角色名缓存连接池。密码读取只在需要解析身份时发生，但已有连接池不会因数据库密文变化自动替换。修改查询账号或密码后需要重启应用。

## 6. 实际授权读取

IdentityService.get_asset_policy 使用配置的管理连接读取查询账号授权。DorisRoleRepository 查询账号的授权记录，并确认预期角色确实绑定在账号上。

解析范围包含全局、Catalog、数据库、表和字段层级的 SELECT 权限，再限定到当前数据源、Catalog 和业务库。不能识别的授权记录会记录日志并跳过，不能凭显示文字猜测成全库权限。

因此权限策略反映的是账号实际授权，而不是角色预设清单的静态副本。手工修改 Doris 授权后，后续策略读取会反映这些变化。

## 7. 资产范围比较

AssetIdentity 按数据源、数据库、表、字段四个维度表示范围。某个层级为 None 时，该层级可匹配任意值。比较由 encompasses 逐项完成。

AssetAccessPolicy 提供两个不同问题的答案：

| 判定       | 含义                     | 示例                                   |
| ---------- | ------------------------ | -------------------------------------- |
| allows     | 是否完整拥有目标范围     | 表级授权允许读取该表内字段             |
| is_visible | 目标或其某个下级是否可见 | 仅能读一列时，表本身仍可作为上下文出现 |

仅有某一列权限时，不能用表可见推导出整表可读。元数据过滤用 allows 选择字段，用 is_visible 选择需要展示的表，并移除未授权主键和引用。

没有任何授权时，策略默认不允许访问。空指标依赖也不能被集合逻辑误判为任何人都能使用；元数据模块要求这类指标具备整库访问权。

## 8. 权限执行的两层保障

元数据过滤控制模型能看到的目录内容。字段索引查询使用白名单，返回后再对照可见目录；指标必须满足所有依赖字段都可访问。

SQL 执行使用该用户角色对应的账号，让 Doris 再次检查表列权限。召回成功不构成 SQL 放行凭据，模型仍可能生成越权或无效 SQL，最终会由数据库拒绝。

授权读取与 SQL 执行不是同一数据库快照。如果权限在两者之间变化，以实际查询时 Doris 的结果为准。

## 9. 用户切换与资源归属

前端保存当前用户选择，切换后清理会话缓存与事件订阅，加载新用户的数据。已经启动的后台 Run 不因前端切换而改变所有者，也不会自动停止。

会话服务始终使用用户 ID 和会话 ID 组合访问资源。附件下载先检查会话归属，再调用沙箱；沙箱自身还会检查文件是否位于目标会话范围。

## 10. 凭据与维护

查询密码使用 Fernet 密文持久化，解密密钥由环境配置提供。加密密钥变化会使已有密文不可解密，更新时要同步处理身份记录。

增加业务角色需要定义明确的业务范围、独立查询账号和用户关联，再执行初始化。验证应包括白名单内查询成功、域外表查询失败、元数据不会暴露域外字段三部分。

出现“看不到表”时依次检查用户关联、账号角色绑定、Doris 实际授权和元数据目录是否已导入。出现“能召回但不能查询”时检查权限变动、SQL 实际引用及连接池凭据，而不是扩大召回权限规避错误。
